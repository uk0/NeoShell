## 2. Critical

### 2.1 SSH host keys are never verified

`ssh2::Session::known_hosts()` is not called anywhere in the tree. Grep across
`core/src/` returns no `known_hosts` usage at all. libssh2 does not verify host
keys on its own — that is the application's job, and the application does not do
it.

Practical effect: NeoShell will complete a handshake with, and send credentials
to, whatever answers on `host:port`. There is no trust-on-first-use record, no
fingerprint display, no warning on change. Anyone positioned on the path gets
the password or, for key auth, a live authenticated session.

The reconnect path makes this worse. `core/src/ssh/mod.rs:846-870` retries up to
ten times with backoff after a link drop, re-authenticating each time from a
`ConnectParams` that holds the plaintext password. A network interruption is
exactly when an attacker would be in position, and the client will walk straight
back into it.

What makes this easy to miss on a skim: the error translator at
`core/src/ssh/mod.rs:87` maps host-key errors to a user-facing string, and
`core/src/i18n.rs:246` reads *"host key changed — server may have been
reinstalled, or this could be a MitM attack"*. There is also a passing test,
`ssh::error_tests::host_key_mismatch_gets_hint`. All of it is translation
machinery for an error libssh2 will never raise here. The code looks like it
handles host keys. It does not.

### 2.2 The update channel is an unsigned code-execution path

`core/src/updater.rs` downloads a shared library and `launcher/src/main.rs`
`dlopen`s it and calls into it. The only integrity check is an MD5 compared
against a value fetched from the same JSON document that supplies the download
URL (`updater.rs:227-238`).

Two separate problems:

**Same-source integrity.** Whoever serves `update.json` controls both the URL
and the expected digest. A compromised host, CDN, or TLS-terminating middlebox
substitutes both and the check passes. MD5 here only catches transport
corruption; it provides no authenticity at all. There is no signature and no
pinning.

**Verification is skipped entirely at apply time.** `apply_pending_update()`
(`launcher/src/main.rs:78-105`) renames whatever file sits at
`~/Library/Application Support/neoshell/updates/libneoshell_core.dylib` over the
live library. No hash, no signature, no provenance check. Any local process that
can write that path gets code execution as the user on next launch, bypassing
even the MD5.

### 2.3 Update rollback cannot fire

The recovery path in `launcher/src/main.rs:18-26` looks for a `.bak` when
`Library::new()` fails. But `apply_pending_update()` deletes that backup at
lines 107-111, in the same call, *before* the library is ever loaded:

```rust
// Clean old backup if exists and library loads fine
let bak = lib_path_with_ext(lib_path, "bak");
if bak.exists() && lib_path.exists() {
    let _ = std::fs::remove_file(&bak);
}
```

The comment says "if ... library loads fine". Nothing has loaded anything at
that point. Sequence on a bad update: back up, swap in, delete backup, try to
load, fail, look for backup, find nothing, `exit(1)`. A broken core library is
unrecoverable without manual reinstall.

Combined with 2.2, a hostile or merely corrupt update is permanent.

## 3. High

### 3.1 Bastion and tunnel credentials bypass the vault

The project's stated model is AES-256-GCM under an Argon2id-derived key. Two
credential stores sit outside it.

`core/src/proxy.rs:17-34` — `ProxyConfig` carries `password`, `private_key` and
`passphrase`. `ProxyStore::save()` at line 89-92 writes them to `proxies.json`
via `std::fs::write`, serialized as plain JSON.

`core/src/tunnel.rs` — `TunnelConfig` carries the same three fields and writes
`tunnels.json` the same way at line 106.

These are bastion-host credentials. In most deployments the jump host is the
more privileged of the two hops. They are stored in cleartext, at default umask
permissions, while the target-host credentials next to them are encrypted.

Only `core/src/sshkeys.rs:113-115` sets restrictive modes (0600/0644). Every
other write — `vault.json`, `proxies.json`, `tunnels.json`, `alerts.json`,
`snippets.json`, `theme.json` — uses default permissions, which on macOS with a
022 umask means world-readable.

### 3.2 Tunnels connect before the vault is unlocked

`core/src/app.rs:1125-1139`, inside `impl Default for NeoShell`:

```rust
tunnel_manager: {
    let mgr = Arc::new(crate::tunnel::TunnelManager::new());
    let ts = crate::tunnel::TunnelStore::new();
    for t in ts.load() {
        if t.auto_start {
            mgr.start(t.clone())
        }
    }
    mgr
},
```

`screen` is set to `Screen::Locked` a few lines earlier. So on launch, the app
reads plaintext credentials from `tunnels.json`, opens authenticated SSH
sessions and binds local forwards — and only then shows the master-password
prompt. Anyone with the laptop open gets working forwards into the tunnel's
network without knowing the master password.

Separately: `Default::default()` here performs network I/O and can fail. That
belongs in an explicit constructor.

### 3.3 Vault writes are not atomic and not backed up

`core/src/storage/mod.rs:256-267` serializes the whole vault and calls
`std::fs::write` directly over `vault.json`. No temp file, no rename, no
generation kept. Every connection add, edit and delete rewrites the entire file
in place.

A crash, a full disk, or a power loss during that write truncates the vault and
takes every stored connection with it. There is no second copy anywhere.

Same file, related: `save_connection()` (line 147) and `update_connection()`
(line 228) each do a read-modify-write of the whole file, and `get_connections()`
(line 177) decrypts every entry to build a list view. Fine at ten connections,
not at a thousand.

### 3.4 Argon2 parameters are not recorded in the vault

`derive_key()` at `core/src/crypto/mod.rs:163-172` hardcodes `m=65536, t=3, p=4`.
`VaultHeader` (lines 10-17) stores salt, nonces, the wrapped DEK and a
verification token — but not the KDF parameters, and no format version field.

The moment those parameters are raised (and they should be raised — 64 MiB / 3
passes is at the low end today), every existing vault becomes undecryptable,
because unlock will derive a different KEK from the same password with no way to
know it should have used the old cost. There is no migration path because there
is nothing to migrate against.

This is cheap to fix now and expensive to fix after users have vaults.

### 3.5 Version comparison is a string compare

`core/src/updater.rs:160`:

```rust
if info.version != current_version && info.version > current_version.to_string() {
```

`>` on `String` is lexicographic. `"0.10.0" > "0.9.0"` evaluates to `false`. The
updater will stop offering updates the moment the project reaches 0.10.0, and it
will silently stop — no error, the branch just takes the `Ok(None)` path.

The same comparison permits downgrades from the server side: there is no
monotonic floor, so a served `version` that sorts high but is semantically older
(`"0.9.9"` against a running `"0.10.1"`) is accepted and installed.

## 4. Medium

### 4.1 Private keys are copied to a temp file for a retry that cannot work

Five sites (`core/src/ssh/mod.rs:617-621, 697-700, 1663-1665, 1738-1740`, and
around 1887) follow the same shape:

```rust
Err(e) => {
    log::warn!("pubkey_file failed ({}), trying in-memory key auth", e);
    // Read key content and try userauth_pubkey_frommemory
    // Fallback: write key to temp file and retry
    let tmp_key = std::env::temp_dir().join(format!("neoshell_key_{}", uuid));
    std::fs::copy(key_path, &tmp_key)?;
    let result = session.userauth_pubkey_file(username, None, &tmp_key, passphrase);
    let _ = std::fs::remove_file(&tmp_key);
    ...
    log::info!("SSH key auth succeeded via in-memory pubkey");
}
```

The fallback calls the identical function on a byte-identical copy of the same
file. If the first call failed for any reason other than a transient read error,
the second fails the same way. The comments describe `userauth_pubkey_frommemory`
and the success log claims "in-memory pubkey"; neither is what the code does.

The cost is that the private key lands on disk at a second location. `remove_file`
is best-effort — if the process dies in between, the copy stays. At line 698 the
key material is written from memory rather than copied, which also means the
0600 mode is not carried over from the source file.

This block should either be deleted or actually implement in-memory auth.

### 4.2 A missing proxy silently becomes a direct connection

`establish_tcp()` in `core/src/ssh/mod.rs`:

```rust
// proxy_id set but proxy not found — fall through to direct
log::warn!("Proxy '{}' not found, connecting directly", proxy_id);
```

If a connection is configured to reach its target through a bastion and the
bastion entry is missing, NeoShell connects straight to the target instead. That
is a network boundary the user asked for being crossed without consent, with
only a log line. It should fail closed.

### 4.3 Key material is never zeroized

`CryptoEngine.dek` is a plain `[u8; 32]`. `derive_key()` returns the KEK by
value, leaving copies on the stack. Passwords move through `&str` and `String`.
Decrypted connection blobs are `Vec<u8>`. The `zeroize` crate is not a
dependency.

Every one of those stays in the process image until the allocator reuses it, and
lands in any core dump or swap page. For a credential manager this is a
reasonable thing to get right.

### 4.4 The vault never re-locks

`Screen::Locked` is set in exactly one place — `core/src/app.rs:1034`, at
construction. There is no manual lock action and no idle timeout. Meanwhile the
window close button is intercepted (`core/src/app.rs:4299-4306`) and converted to
a minimize so sessions survive.

So the intended usage is a long-lived resident process, and in that process the
DEK is live in memory from first unlock until reboot. The master password
protects the first thirty seconds of the day and nothing after.

### 4.5 Two polling loops, neither of them necessary

`core/src/app.rs:4296`:

```rust
time::every(Duration::from_millis(50)).map(|_| Message::PollSshEvents),
```

Unconditional, 20 Hz, running on the setup and unlock screens as well as the main
one. Each tick enters a 2,906-line `update()` and drives an iced redraw.

Per session, `core/src/ssh/mod.rs:832` sleeps 10 ms between non-blocking reads —
100 wakeups per second per open session.

iced 0.13 supports channel-backed subscriptions; the SSH threads should push into
one rather than the UI asking twenty times a second whether anything happened.

Related, and more visible to users: the drain at `core/src/app.rs:2007` is
`while let Ok(event) = rx.try_recv()` with no per-tick budget. A remote producing
output faster than the UI consumes it (`cat` on a large file, a chatty build)
means one tick processes an unbounded backlog synchronously on the UI thread. The
window stops responding until it clears. A byte budget per tick fixes it.

### 4.6 The logger does three syscalls per line under a global mutex

`core/src/lib.rs:69-94` opens, appends, and closes the log file for every single
record, plus a `create_dir_all` each time, all inside one process-wide mutex.

The justification in the comment is that `rm neoshell.log` mid-run should be
handled. That is a rare operation being paid for on every line written, by every
thread, with lock contention between them.

Two smaller issues in the same area. `chrono_now()` (line 100) derives hours from
the Unix epoch with no timezone handling and no date — log lines read
`[14:23:07.412 INFO ...]` and you cannot tell what day that was without checking
file mtime, which rotation then destroys. The comment calls it "local time",
which it is not; it is UTC. And rotation is checked only at startup, so a
long-running session grows past the 2 MB ceiling without bound.

### 4.7 No panic barrier at the FFI boundary

`neoshell_run()` (`core/src/lib.rs:19`) is `extern "C"` with no `catch_unwind`.
The release profile sets `panic = "abort"`. Any panic anywhere in the ~10k lines
of UI code takes the process down immediately — no vault flush, no session
cleanup, and because the launcher hosts the library in-process, no restart.

Given that the rollback path is already dead (2.3), there is currently no failure
mode from which the application recovers on its own.

### 4.8 Downloads are unbounded

`download_update()` (`core/src/updater.rs:196-225`) uses `download.size` only to
compute the progress fraction. The read loop writes whatever the server sends. A
wrong or hostile `Content-Length` fills the disk. There is also no guard against
two concurrent `download_async()` calls writing the same staging path.

### 4.9 Configuration saves fail silently

`let _ = std::fs::write(...)` appears at `proxy.rs:91`, `tunnel.rs:106`,
`theme_config.rs:81`, and `app.rs:371, 444, 972, 992, 1024`. Across the tree
there are 25 `let _ =` in `app.rs` and 21 in `ssh/mod.rs`.

Where the discarded result is a save, the user's change appears to take effect in
the UI and is gone on restart, with no message and no log line.

### 5.5 Dependencies

### 5.7 What is in good shape

Worth recording, so the fix work does not disturb it:

- Terminal emulation is the strongest module. 16 tests cover SGR, erase modes,
  scroll regions, resize-with-scrollback, CJK width, zero-width and variation
  selectors. Scrollback is bounded at 10,000 lines.
- `unwrap`/`expect` discipline is good: one `unwrap` in 10k lines of `app.rs`,
  none in crypto, storage or terminal. The only `panic!` in library code is
  inside a `#[cfg(test)]` block.
- The crypto construction itself is sound — Argon2id, a wrapped DEK so the master
  password can change without re-encrypting everything, a verification token,
  fresh 96-bit nonces from `OsRng` per operation. The problems in section 3 are
  around it, not in it.
- i18n is balanced at 314 keys per locale, en and zh in sync.
- The algorithm self-check (`verify_required_algorithms`) gating the release
  build is a good idea and catches a real class of platform bug.

## 6. Plan

Sequenced so each phase leaves the tree shippable.

### Phase 0 — stop the bleeding (before any release)

Nothing here is a refactor; all of it is contained.

1. **Fix the launcher rollback** (`launcher/src/main.rs`). Move the `.bak`
   deletion to after a successful `Library::new()` and a successful `run()`
   return. Two-line change, removes the "bad update bricks the install" case.
   *Done when:* a deliberately corrupt staged library causes a rollback and a
   normal start on the next launch.

2. **Fix version comparison** (`updater.rs:160`). Parse into `(u64, u64, u64)`
   and compare numerically; reject anything not strictly greater than the
   running version. Add tests for `0.9.0 → 0.10.0`, `0.10.1 → 0.9.9`, and equal.
   *Done when:* those three cases are asserted in `cargo test`.

3. **Cap the download** at `download.size` plus a small margin, and abort on
   overrun.

4. **Set 0600 on every file the app writes.** One helper, called from every save
   path. Include the log — it contains hostnames and usernames.

5. **Stop auto-starting tunnels before unlock** (`app.rs:1125`). Move the loop
   out of `Default` and behind the unlock transition.

6. **Add a CI gate.** New workflow on push and PR: `cargo fmt --check`,
   `cargo clippy --workspace --all-targets -D warnings` (start with the current
   83 baselined via `#[allow]` at the call sites, or accept the warnings and
   tighten later), `cargo test --workspace`. This is the change that keeps the
   rest of the plan from eroding.

### Phase 1 — host key verification

The largest single security gap, and it is self-contained in `ssh/mod.rs`.

- Wire `Session::known_hosts()` against `~/.ssh/known_hosts` in OpenSSH format,
  so entries are shared with the system `ssh` client rather than duplicated.
- Check after `handshake()`, before any `userauth_*` call, on every code path —
  there are six handshake sites (`179`, `410`, `682`, `1647`, `1718`, `1868`)
  and the reconnect path at `846`. They should route through one helper.
- Three outcomes: known and matching → proceed; unknown → show the fingerprint
  and ask, write on accept; **changed → refuse, no override in the dialog.**
- On reconnect, compare against the key recorded for this session and abort on
  mismatch without prompting. A reconnect is not a first contact.
- Surface the current host key fingerprint in the connection detail view.

*Done when:* connecting to a host with a rotated key is refused; the existing
`host_key_mismatch_gets_hint` test is backed by a real code path; a test with a
fixture `known_hosts` covers match, absent, and mismatch.

### Phase 2 — signed updates

- Generate an ed25519 signing key, kept offline. Embed the public key in the
  **launcher** binary, not the core library, so a compromised core cannot
  rotate it.
- Sign the core library at release time in CI; publish the detached signature
  alongside. Keep the MD5 field for transport-corruption detection if you like,
  but it is no longer the security control.
- Verify the signature in two places: in `updater.rs` after download, and again
  in `apply_pending_update()` before the rename. The second one is the one that
  matters — it closes the "anything that can write the staging dir" path.
- Refuse to apply a version not strictly greater than the running one.
- Hash while streaming instead of re-reading the file (`updater.rs:229`).

*Done when:* a staged library with a bad or absent signature is rejected at apply
time and the previous library keeps running.

### Phase 3 — one credential store

- Move `ProxyConfig` and `TunnelConfig` secrets into the vault. Keep the
  non-secret fields (`name`, `host`, `port`, `forwards`, `auto_start`) in their
  current JSON files so the UI can list them while locked; store only
  `password` / `private_key` / `passphrase` as encrypted blobs keyed by id.
- Write a one-shot migration: on first run after upgrade, read the existing
  plaintext `proxies.json` and `tunnels.json`, move the secrets into the vault,
  rewrite the files without them, and overwrite the old bytes before unlinking.
- Make `auto_start` mean "start after unlock".
- Add `version` and the Argon2 parameters (`m`, `t`, `p`) to `VaultHeader`. Read
  them on unlock, default to the current constants when absent so existing
  vaults still open. This unblocks ever raising the cost.
- Make vault writes atomic: write `vault.json.tmp`, fsync, rename. Keep one
  generation as `vault.json.1`.
- Add `zeroize` and apply it to the DEK, the derived KEK, password buffers and
  decrypted blobs.

*Done when:* `grep -r password ~/Library/Application\ Support/neoshell/*.json`
returns nothing outside the encrypted blobs; a kill -9 during a vault save leaves
a readable vault; round-trip and corruption tests exist.

### Phase 4 — decompose `app.rs`

Do this after the security work, and incrementally — no big-bang rewrite. The
seams are already visible in the `Message` enum.

Suggested split, roughly by existing message prefix:

```
app/mod.rs        NeoShell, run(), top-level update/view dispatch
app/session.rs    tabs, splits, terminal I/O, ZMODEM
app/files.rs      SFTP browser, local browser, transfers
app/tunnels.rs    tunnel manager + form
app/monitor.rs    system monitor, process list, alerts
app/palette.rs    command palette, snippets, quick commands
app/dialogs.rs    connect/edit/proxy/key-manager forms
```

Each module owns a sub-enum of `Message` and a sub-struct of state; the top-level
`update()` becomes a dispatch of seven arms. Move one module per commit, keep the
tree compiling, and delete the dead widgets from 5.4 as you pass them.

Set an explicit target so this doesn't drift: **no function over 300 lines, no
file over 1,500.**

### Phase 5 — event-driven I/O

- Replace `Message::PollSshEvents` with an `iced::Subscription` fed by a channel
  the SSH reader threads write into. Removes the 20 Hz idle wakeup.
- Replace the 10 ms sleep in the reader loop (`ssh/mod.rs:832`) with a blocking
  read and a session-level timeout, or `poll()` on the underlying socket.
- If the polling architecture stays for now, at minimum add a per-tick byte
  budget to the drain loop at `app.rs:2007` so a noisy remote cannot freeze the
  window.
- Rework the logger to hold an open handle, or buffer and flush on an interval.
  Give timestamps a date and a real timezone.

### Ongoing

- Introduce a real error type. `thiserror` per module, `String` only at the UI
  boundary. `translate_ssh_error`'s 13 substring matches become a match on
  variants.
- `catch_unwind` around the body of `neoshell_run()` so a UI panic can at least
  flush state and return a distinct exit code.
- Fail closed when a configured proxy is missing (4.2).
- Delete the temp-file key fallback (4.1), or implement
  `userauth_pubkey_frommemory` properly.
- Stop discarding save errors; surface them (4.9).
- Update `CLAUDE.md` to match the actual module list.

---

## 7. Suggested order

Phase 0 is a day or two and should land before anything else ships. Phase 1 and
Phase 2 are the two items that change the product's security posture; of the
two, host key verification is the one users are exposed to every day. Phase 3
is a data migration and wants to land before the user base grows. Phase 4 is
the one that makes the rest cheaper, and it can proceed in parallel with nothing
blocking it — but starting it first would mean doing the security fixes twice,
once in the old layout and once in the new.

Nothing in Phases 0–3 requires touching `app.rs` beyond the tunnel auto-start
move, so the two tracks do not collide.
